# Phase 1.23 Completion Report — Deployment Architecture

## Objective
Design the complete production cloud deployment and hosting architecture for MerQent. Formulate a cost-effective, highly available AWS serverless container architecture utilizing Amazon ECS on AWS Fargate, Amazon Aurora PostgreSQL Serverless v2 (with `pgvector`), Amazon ElastiCache for Redis, Amazon S3 with SSE-KMS, and Cloudflare WAF/Edge routing. Establish Disaster Recovery metrics (RTO < 2h, RPO < 15m) and environment parity across Local, Staging, and Production.

## Work Completed
1. Formulated complete deployment architecture in `docs/architecture/23-deployment-architecture.md`:
   - Designed production AWS VPC network topology across public, private application, and isolated data subnets in a Multi-AZ configuration.
   - Standardized container hosting on Amazon ECS Fargate (2+ tasks each for Next.js Web, NestJS API, and BullMQ Workers), eliminating Kubernetes operational cluster overhead.
   - Formulated database hosting using Amazon Aurora PostgreSQL Serverless v2 with native `pgvector` and automated Multi-AZ failover.
   - Configured Amazon ElastiCache Redis cluster for cache, BullMQ queues, and SSE Pub/Sub event streams.
   - Formulated 3-tier environment isolation: Local (Docker Compose), Staging (mirrored AWS VPC), and Production (hardened Multi-AZ).
   - Engineered Disaster Recovery framework achieving RPO < 15 minutes (Aurora PITR) and RTO < 2 hours (Terraform IaC and cross-region snapshot replication).
   - Formulated cost optimization model demonstrating an early-stage baseline run rate of ~$320/month.

## Decisions Made
- **ECS Fargate over Kubernetes (EKS):** Avoided premature Kubernetes complexity for Phase 1-2. ECS Fargate provides automated scaling, managed security patching, and zero worker-node maintenance.
- **Aurora PostgreSQL Serverless v2:** Replaces fixed-size database instances with dynamic compute scaling (2 to 8 ACUs), providing high availability during peak PE search traffic while dropping costs during idle hours.
- **Local Development Parity:** Provided Docker Compose configuration enabling developers to run identical database extensions and Redis queues locally with zero cloud dependencies.

## Issues Found
- Ingress routing complexity if separate hostnames were required for Web and API.
- Resolution: Application Load Balancer path-based routing directs `/api/*` to the NestJS API service and `/*` to the Next.js Web service under a unified domain (`merqent.com`).
