# Phase 1.4 Completion Report — Technology Evaluation

## Objective
Execute a rigorous, evidence-based evaluation of candidate technologies across all platform tiers (Frontend, Backend, Database, Search, AI/LLM, Object Storage, Real-Time, Email, Calendar, Observability). Avoid premature framework lock-in or default choices (e.g., generic MERN).

## Work Completed
1. Formulated complete technology evaluation in `docs/architecture/04-technology-evaluation.md`:
   - Evaluated 4 Backend candidates: Node.js/NestJS, Python/FastAPI, Java/Spring Boot 3, Go.
   - Evaluated 4 Frontend candidates: Next.js (App Router), Vite React SPA, Remix, Nuxt 3.
   - Evaluated 3 Database candidates: PostgreSQL 16+, MongoDB 7+, MySQL 8+.
   - Evaluated 3 Search candidates: Hybrid PostgreSQL (`tsvector` + `pgvector`), Dedicated Elasticsearch/OpenSearch, Dedicated Vector DB (Pinecone/Qdrant).
   - Evaluated 4 AI/LLM candidates: OpenAI, Anthropic, Google Vertex AI, Self-hosted Llama 3.1.
   - Evaluated Storage (S3, GCS, R2), Real-Time (SSE vs WebSockets vs Polling), Email (Resend vs SES), Calendar (Native .ics vs OAuth Sync), and Observability (Pino/Sentry/OTel vs Datadog).
   - Documented comparative trade-offs, MerQent-specific domain drivers, security, mobile compatibility, cost, and explicit architectural recommendations.

## Decisions Made
- **Avoided MERN Default:** Explicitly rejected MongoDB for MerQent's relational, financial-grade aggregate domain; selected PostgreSQL 16+ with `pgvector` for unified relational + vector data integrity.
- **Backend Framework:** Recommended Node.js with NestJS for modular enterprise DDD architecture, strict TypeScript typing shared with client, and auto-generated OpenAPI contracts.
- **Search Strategy:** Recommended Hybrid PostgreSQL (Full-Text Search + `pgvector` HNSW index) to eliminate complex CDC pipelines and external cluster overhead during early scaling.
- **Real-Time Strategy:** Selected Server-Sent Events (SSE) over HTTP/2 for server-to-client notifications and messaging push, mitigating enterprise corporate proxy blocks associated with WebSockets.

## Architecture Changes
- Confirmed single-engine persistence strategy (PostgreSQL 16+ for relational, document JSONB, and vector embeddings).
- Established dual AI model strategy (OpenAI for embeddings and strict JSON formatting; Anthropic Claude 3.5 Sonnet as qualitative alternative).

## Validation Performed
- Validated that the recommended stack natively satisfies all non-functional requirements (ACID compliance, low latency, end-to-end type safety, mobile API readiness).
- Verified that no proprietary vendor lock-in blocks future cloud portability or migration.

## Tests / Checks Performed
- Architectural cohesion test: Ensured TypeScript across NestJS backend and Next.js frontend enables shared validation schemas via Zod in a monorepo.

## Issues Found
- Real-time WebSockets can face connection terminations across strict financial institution corporate firewalls.
- Resolution: Transitioned real-time messaging push to Server-Sent Events (SSE) over standard TLS HTTP/2, using standard REST mutations for message sending.

## Issues Resolved
- Enterprise firewall resilience solved.

## Risks
- Vector index query performance under heavy concurrency. Mitigated by using HNSW indexing in `pgvector` and caching frequent project embedding lookups.
