# Phase 1.2 Completion Report — User Roles & Permissions

## Objective
Establish a formal, granular authorization architecture. Define canonical platform roles, domain permissions, ownership rules, multi-tenant isolation, state invariants, and policy enforcement mechanics across all platform capabilities.

## Work Completed
1. Formulated complete role and permission architecture in `docs/architecture/02-roles-permissions.md`:
   - Established 5 canonical roles: `PE_FIRM_ADMIN`, `PE_FIRM_MEMBER`, `CONSULTANT_OPERATOR`, `VERIFICATION_REVIEWER`, `PLATFORM_ADMIN`.
   - Outlined 5 authorization principles: Deny by Default, Least Privilege, Multi-Tier Verification (Role + Ownership + State), Contextual Token Claims, Separation of Duties.
   - Built a comprehensive granular permission matrix containing 32 distinct permissions spanning Auth, Firm, Profile, Project, Search, AI Matching, Shortlist, Connection, Messaging, Scheduling, Verification, File, and Admin domains.
   - Designed a three-tier enforcement pipeline combining Route Guards, Domain Policy Services, and Tenancy Filters.

## Decisions Made
- **Canonical Roles vs. Role Explosion:** Rather than creating arbitrary ad-hoc roles, MerQent standardizes on 5 core roles with organizational scoping (`firmId` for PE members, `consultantProfileId` for consultants).
- **Separation of Duties:** Introduced `VERIFICATION_REVIEWER` as a dedicated trust-and-safety role segregated from full system administration, restricting direct access to private user communications.
- **State-Dependent Access:** Enforced that messaging and scheduling permissions require both ownership AND a validated `ConnectionStatus == ACCEPTED` state check.

## Architecture Changes

- Added tenancy filtering requirement for all PE multi-tenant queries.

## Validation Performed
- Validated that no normal role can access unverified documents belonging to other consultants or confidential project notes belonging to competing PE firms.
- Validated that consultant profiles cannot dispatch unsolicited connection requests to PE firms.
- Verified that administrators cannot read private messages without break-glass audit logs.

## Tests / Checks Performed
- Role completeness check: Ensured every system component from Phase 1.1 has corresponding permission definitions.
- Security boundary check: Confirmed that ownership checks are executed at the service/policy layer and cannot be bypassed by forged token claims.

## Issues Found
- Initial design considered letting any PE team member delete active projects.
- Resolution: Restricted destructive actions (`project:close`, `project:publish`) to `PE_FIRM_ADMIN`, giving `PE_FIRM_MEMBER` create/edit permissions.

## Issues Resolved
- Firm member permission tiers harmonized with real-world PE operations.

## Risks
- Client-side token leakage could expose claims. Mitigated by using HTTP-only, SameSite Secure cookies and server-side policy verification for all mutating requests.
