## 1. Executive Summary & Verification Verdict

### Verdict: ACCEPTED & FULLY VERIFIED
An exhaustive security audit and verification was conducted on MerQent's Task 2.R3 database guard architecture. Three critical safety improvements and boundary hardening measures were implemented and regression-tested:

1. **Docker Host Untrusted by Default**: Container service names (`merqent_postgres`, `postgres`, `db`, `host.docker.internal`) are no longer unconditionally whitelisted in `LOCAL_HOST_WHITELIST`. They are classified as `DOCKER_SERVICE` and rejected by default; `--force` alone cannot reset a container service without an explicit authorized remote maintenance override.
2. **Ambiguous Targets Fail Closed**: Single-label bare hostnames, missing hostnames, missing/empty database paths, and malformed URLs are classified as `AMBIGUOUS` and fail closed. The remote maintenance override **never** bypasses ambiguous target validation.
3. **Comprehensive Wrapper Hardening**: Both PowerShell (`reset-db.ps1`) and Bash (`reset-db.sh`) wrappers were tested and verified to reject cloud, remote, Docker, and malformed/missing targets before reaching Prisma. `--force` strictly satisfies local confirmation and cannot bypass environment, remote-target, or target-validation protections.

Zero destructive operations were executed against any real database during this audit.

## 2. Audit Area 1: Target Classification & Ambiguity Auditing

### 2.1. Target Classification Matrix
The guard engine (`scripts/database/db-guard.js`) defines five formal security classifications:

| Category | Classification Token | Criteria & Hostname Examples | Default Policy |
| :--- | :--- | :--- | :--- |
| **Local Loopback** | `LOCAL_LOOPBACK` | Guaranteed host-local loopback: `localhost`, `127.0.0.1`, `::1`, `[::1]`, `0.0.0.0`, or `127.0.0.0/8` IP addresses. | Permitted with explicit confirmation (`--force` or `CONFIRM_DB_RESET=YES`) when not in production. |
| **Docker Service** | `DOCKER_SERVICE` | Container network services: `merqent_postgres`, `postgres`, `db`, `database`, `host.docker.internal`, `docker.for.mac.localhost`. | **REJECTED by default (`DOCKER_HOST_NOT_TRUSTED`)**. Cannot be reset by `--force` alone. Requires authorized maintenance override. |
| **Remote / Shared** | `REMOTE_SHARED` | Non-local network hosts with domain dots or private IP ranges: `staging-db.merqent-internal.net`, `10.0.1.50`, etc. | **REJECTED by default (`REMOTE_DATABASE_BLOCKED`)**. Requires authorized maintenance override. |
| **Cloud / Production** | `CLOUD_OR_PRODUCTION` | Cloud providers: `*.rds.amazonaws.com`, `*.database.azure.com`, `*.supabase.co`, `*.neon.tech`, `*.render.com`, or hostnames containing `prod`, `production`, `live`, `cluster`. | **PERMANENTLY BLOCKED (`PRODUCTION_TARGET_BLOCKED`)**. Never bypassable. |
| **Ambiguous Target** | `AMBIGUOUS` | Bare single-label hostnames (`my-server`), missing hostnames, missing/empty database names, or invalid connection syntax. | **FAIL CLOSED (`AMBIGUOUS_TARGET_BLOCKED`)**. Never bypassable. |

### 2.2. Proof: Docker Hostnames Not Trusted Merely by Name
Previously, `merqent_postgres` and `postgres` were in a flat set of local hosts. In containerized production environments (e.g. `docker-compose.prod.yml`, Kubernetes, ECS), a production database is frequently assigned the network alias `postgres` or `merqent_postgres`.

- **Hardening Applied**: `merqent_postgres` and `postgres` were removed from loopback trust and reclassified as `DOCKER_SERVICE`.
- **Verified Behavior**: Passing `--force` against `postgresql://merqent:pass@merqent_postgres:5432/merqent_dev` is now rejected with `DOCKER_HOST_NOT_TRUSTED`.

## 4. Audit Area 3: Destructive Entry Points & Coverage

An audit of all scripts, configurations, and CI workflows verified complete coverage:

| Entry Point | Scope | Guard Enforcement | Status |
| :--- | :--- | :--- | :--- |
| `pnpm run db:reset` | Root `package.json:31` | Invokes `node scripts/database/db-guard.js && prisma migrate reset ...` | **Enforced** |
| `pnpm run prisma:reset` | Root `package.json:43` | Alias to `pnpm run db:reset`, invoking guard | **Enforced** |
| `pnpm --filter=@merqent/api run db:reset` | `apps/api/package.json:17` | Invokes `node ../../scripts/database/db-guard.js && prisma migrate reset ...` | **Enforced** |
| `pnpm --filter=@merqent/api run prisma:reset` | `apps/api/package.json:18` | Invokes `node ../../scripts/database/db-guard.js && prisma migrate reset ...` | **Enforced** |
| `.\scripts\database\reset-db.ps1` | PowerShell Reset Script | Invokes `node scripts/database/db-guard.js --force $RemainingArgs` | **Enforced** |
| `./scripts/database/reset-db.sh` | POSIX Bash Reset Script | Invokes `node scripts/database/db-guard.js --force "$@"` | **Enforced** |
| `pnpm run db:migrate` / `prisma:migrate` | Root & API | Runs `prisma migrate deploy` (forward-only, non-destructive) | **Preserved** |
| `pnpm run db:seed` / `prisma:seed` | Root & API | Runs idempotent `upsert` queries (non-destructive) | **Preserved** |

### Intentionally Unsupported Direct CLI Invocations & Limitations
- **Direct Terminal CLI Execution (`npx prisma migrate reset`)**: If a developer with direct shell access bypasses `package.json` scripts and runs `npx prisma migrate reset --force` directly, the npm wrapper hook cannot intercept it.
- **Mitigation**: Production environments do not grant interactive shell access, production container images contain compiled binaries without development CLI tools, and automated deployment pipelines exclusively invoke `pnpm run db:migrate` (`prisma migrate deploy`).

## 5. Audit Area 4: Wrapper Behavior & `--force` Boundary Testing

Both wrappers were executed in isolated test runs across four unsafe target configurations:

```
Docker host    => PS exit: 1 | Bash exit: 1
Remote host    => PS exit: 1 | Bash exit: 1
Missing URL    => PS exit: 1 | Bash exit: 1
Ambiguous host => PS exit: 1 | Bash exit: 1
```

### Verified Wrapper Guarantees
1. `--force` satisfies **only** the local confirmation prompt. It **never** bypasses `NODE_ENV=production`, cloud hosts, remote hosts, Docker hosts, or ambiguous targets.
2. If `db-guard.js` fails with exit code 1, both wrappers terminate immediately. The destructive Prisma command is **never** executed.
3. Windows PowerShell 5.1 compatibility: All non-ASCII characters (em-dashes, Unicode checkmarks) were sanitized to standard ASCII, preventing encoding corruption during automated execution.
4. Bash compatibility: `set -euo pipefail` ensures instantaneous script termination on non-zero guard exit codes.
