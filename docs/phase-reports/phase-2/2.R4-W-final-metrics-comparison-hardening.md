## 2. Hardened Comparison Architecture & Security Boundary Claims

### 2.1. Implementation (`safeCompare`)
```typescript
private safeCompare(candidate: string, target: string): boolean {
  if (!candidate || !target) return false;
  try {
    const hashCandidate = crypto.createHash('sha256').update(candidate, 'utf8').digest();
    const hashTarget = crypto.createHash('sha256').update(target, 'utf8').digest();

    return crypto.timingSafeEqual(hashCandidate, hashTarget);
  } catch {
    return false;
  }
}
```

### 2.2. Precise Scope of Timing Protections

#### What This Strategy Protects Against:
- **Length-Mismatch RangeError Elimination**: In standard Node.js `crypto.timingSafeEqual(a, b)`, unequal buffer lengths immediately throw `RangeError: Input buffers must have the same length`. By hashing both inputs with SHA-256 first, both operands are guaranteed to be exactly 32 bytes in length, eliminating runtime crashes and preventing HTTP 500 errors.
- **Secret Extraction via Byte-by-Byte Timing Oracles**: Comparing the 32-byte digests in constant time prevents remote timing attackers from extracting the configured secret character-by-character based on early-return comparison differences.
- **Zero Information Leakage**: Input secrets and tokens are never logged or echoed in error responses.

#### What This Strategy Does NOT Protect Against:
- **Whole-Request Timing Invariance**: It does **not** claim that the entire HTTP request lifecycle is mathematically constant-time. Variable overhead exists across HTTP parsing, TLS termination, JSON serialization, and payload length variations.
- **Hashing Execution Variance**: SHA-256 computation time scales slightly with input byte length (chunked in 64-byte blocks), though this only reflects the candidate input length submitted by the client, not the server's secret.
- **Network & CPU Jitter**: It does not eliminate external packet transmission jitter, TCP retransmission, or host kernel CPU scheduling variations.
