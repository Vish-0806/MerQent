## 1. Executive Summary

Task 2.14.1 resolves specific file storage security concerns identified during the initial review of Task 2.14. In multi-tenant environments managing confidential Private Equity deal flow, loose assumptions regarding asynchronous malware scanning, presigned upload limits, or background cleanups can introduce critical security vulnerabilities.

This remediation establishes strict, production-oriented security controls across four key domains:

1. **Malware Status Enforcement (Fail-Closed Architecture)**: Upload confirmation no longer marks files `CLEAN` merely because size and storage presence checks pass. When the malware scanner is unattached/inactive (`isLive = false`) or experiences timeouts/errors, the system strictly fails closed: files remain in `PENDING` state. Download requests are strictly forbidden unless the file has been verified `CLEAN` by an active scanner daemon.
2. **Upload Size Enforcement & Oversized Object Cleanup**: Addressed the architectural limitation of S3-compatible PUT presigned URLs (which cannot enforce range boundaries before receiving bytes). Implemented dual-control enforcement: pre-upload validation rejecting requests with declared size > 25 MB, and post-upload verification via `HeadObjectCommand` during `confirmUpload`, immediately deleting and discarding any object exceeding 25 MB (`26,214,400` bytes) from both storage and the database.
3. **Cleanup Authorization & Race Safety**: Secured `/files/cleanup` against unauthorized access with both `@Roles(UserRole.PLATFORM_ADMIN)` guard enforcement and internal service-level permission checks. Re-architected cleanup logic to be atomically race-safe against concurrent confirmation, deletion, and duplicate worker executions using conditional `deleteMany` operations.
4. **Security Report Consistency & Advisory Reconciliation**: Reconciled the Windows Next.js advisory identifier in Task 2.14 documentation against the official advisory validated in Task 2.13.3 (`GHSA-p293-qw3h-jr36` / CVE-2026-75604). Clarified all security claims to accurately distinguish active controls from currently unattached external dependencies.

## 2. Detailed Remediation Actions

### 2.1 Malware Status Fail-Closed Enforcement

- **State Transition Audit**: Every upload begins in `PENDING` status.
- **Fail-Closed Scanner Boundary (`BoundaryMalwareScannerService`)**: When `isLive = false`, the scanner returns `isClean: false` with status `PENDING` and details `'Antivirus scanner daemon is unattached or inactive'`.
- **Confirmation Handling (`FilesService.confirmUpload`)**:
  - If `isLive = false`: File size and checksum are recorded, but status remains strictly `PENDING`. Logged with a security warning.
  - If `isLive = true` but scanner times out or throws: Fails closed. Status remains `PENDING`.
  - If `scanResult.status === INFECTED`: Object is deleted from storage immediately, record marked `INFECTED`, and `403 Forbidden` (`ErrorCode.MALWARE_DETECTED`) is thrown.
  - Only when `isLive = true`, `isClean = true`, and `status === CLEAN`: Status transitions to `CLEAN`.
- **Download Clearance Enforcement (`FilesService.getDownloadUrl`)**:
  - `INFECTED` files: Rejected with `403 Forbidden` (`ErrorCode.MALWARE_DETECTED`).
  - `PENDING` or unverified files: Rejected with `403 Forbidden` (`ErrorCode.FILE_ACCESS_DENIED`, `'Access prohibited: File is unavailable for download until malware scanning has cleared it'`).
  - Only `CLEAN` files are issued short-lived presigned download URLs.

### 2.2 Upload Size Enforcement & Oversized Object Cleanup

- **S3 PUT Presigned URL Limitation**: S3-compatible endpoints do not support range-based max-size boundaries on PUT requests prior to receiving bytes. The SDK binds declared `ContentLength` into the signature, but if a client streams more bytes, MinIO/S3 accepts the payload into storage unless the client sent a mismatched `Content-Length` header.
- **Pre-Upload Enforcement**: `PresignUploadSchema` and `FilesService.requestUpload` reject any upload request with declared `fileSizeBytes > 26,214,400` (25 MB) with `400 Bad Request` (`ErrorCode.FILE_TOO_LARGE`).
- **Post-Upload Inspection & Cleanup**:
  - During `confirmUpload`, `HeadObjectCommand` inspects the actual `contentLength` stored in S3.
  - If `contentLength > 26,214,400` (e.g., 25 MB + 1 byte): The oversized object is deleted immediately from S3 (`storage.deleteFile`), the database record is purged, and `400 Bad Request` is thrown.
  - If `contentLength === 0`: The empty object is deleted immediately from S3, the database record is purged, and `400 Bad Request` is thrown.

### 2.3 Cleanup Authorization & Race Safety

- **Authorization Protection**:
  - `@Roles(UserRole.PLATFORM_ADMIN)` applied to `POST /files/cleanup` in `FilesController`.
  - Service-level role assertion in `FilesService.cleanupAbandonedUploads` ensuring only `PLATFORM_ADMIN` users can execute cleanup. Non-administrators receive `403 Forbidden`.
- **Atomic Race Safety**:
  - Replaced unqualified `prisma.fileRecord.delete` with conditional `prisma.fileRecord.deleteMany`:
    ```typescript
    const deleteResult = await this.prisma.fileRecord.deleteMany({
      where: {
        id: record.id,
        scanStatus: FileScanStatus.PENDING,
        createdAt: { lt: cutoffDate },
      },
    });
    ```
  - If a user concurrently confirms the upload (transitioning `scanStatus` from `PENDING` to `CLEAN`), or another job deletes the record, `deleteResult.count === 0`.
  - The backing S3 storage object is deleted **only if** `deleteResult.count > 0`. Valid or concurrently confirmed tenant documents are never deleted.
  - Wrapped `storage.deleteFile` in a try/catch to gracefully handle already-deleted storage objects without aborting the batch cleanup.
