## 1. Executive Summary

Task 2.13.1 resolves and formally assesses the outstanding security risks identified during the Task 2.13 security baseline review. Because MerQent handles sensitive Private Equity deal negotiations, proprietary consultant verification records, and institutional mandate telemetry, all external threat surfaces and failure modes must be explicitly governed and defended.

This remediation addresses three core findings:
1. **Dependency Audit Remediation**: Active dependency overrides and safe patch updates resolved **42 vulnerability notifications**, reducing the workspace vulnerability count from 77 down to 35 (over 54% reduction) with zero breaking changes or tech stack destabilization.
2. **Trusted Deployment Proxy Configuration**: Replaced vulnerable manual `X-Forwarded-For` header parsing with Express-native trusted proxy resolution governed by `TRUST_PROXY`. Direct untrusted client connections can no longer bypass IP rate limiting or poison request context via forged headers.
3. **Explicit Redis Failure Policy**: Defined, implemented, and tested production policies for authentication rate limiting when Redis is unavailable. Implemented configurable `RATE_LIMIT_REDIS_FAIL_CLOSED`, structured security alerts (`SECURITY ALERT`), degraded-mode response headers (`X-RateLimit-Degraded`), and tested `503 Service Unavailable` rejection in fail-closed mode.

#### 1. Next.js 14 Upstream Framework Advisories (33 total)
- **Affected Package**: `next@14.2.35`

- **Technical Barrier**: Upgrading to Next.js 15 requires migrating from React 18 to React 19 and fundamentally refactoring the App Router layer (all page/layout `params` and `searchParams` become asynchronous Promises). - **Exposure Assessment**:
  - Image Optimization remote code execution / DoS: Image domains are restricted to local static assets and pre-verified storage endpoints; external remote images are forbidden.
  - Server Action SSRF / DoS: MerQent uses client-side REST API calls against the NestJS backend via `@merqent/api-client`; Next.js Server Actions are not utilized on public endpoints.
  - Cache Poisoning: Sensitive B2B mandate and deal routes do not use Next.js edge caching / ISR.

## 3. Trusted Proxy Configuration & Anti-Spoofing Architecture

### The Problem
Previously, client IP extraction in `RateLimitGuard` and `CorrelationIdMiddleware` checked `req.headers['x-forwarded-for']` directly. If an attacker connected directly to the API without an intervening proxy and supplied `X-Forwarded-For: 1.1.1.1`, the rate limiter and logger would believe the client IP was `1.1.1.1`, allowing trivial rate-limit bypass by rotating the header.

### The Remediation
1. **Schema & Config Additions**: Added `TRUST_PROXY` to `envConfigSchema` and `AppConfiguration` (default: `'false'`).
2. **Express Engine Binding**: In `main.ts`, configured `app.getHttpAdapter().getInstance().set('trust proxy', trustProxySetting)`.
3. **Strict Trusted Resolution**:
   - In `RateLimitGuard`:
     ```ts
     private getClientIp(req: Request): string {
       return req.ip || req.socket?.remoteAddress || '127.0.0.1';
     }
     ```
   - In `CorrelationIdMiddleware`:
     Checks `req.app.get('trust proxy')`. When `trust proxy` is false/disabled, forged `X-Forwarded-For` headers are strictly ignored and `req.ip` is enforced.
4. **Automated Verification**:
   - Added unit test in `rate-limit.guard.spec.ts` asserting that direct client requests use `req.ip`.
   - Added unit test in `rate-limit.guard.spec.ts` verifying that forged `x-forwarded-for: 10.0.0.99` from direct clients is ignored and rate-limiting is bound to authoritative `req.ip`.
   - Added unit test in `correlation-id.middleware.spec.ts` asserting that forged proxy headers are ignored when `trust proxy` is false.

## 4. Redis Failure Policy & Production Resilience

### The Problem
In multi-replica deployments (e.g., Kubernetes or AWS ECS with 10 pods), falling back to local memory without alerts allows an attacker to achieve `10x` higher brute-force attempts without detection.

### The Remediation
1. **Configurable Failure Policy**: Added `RATE_LIMIT_REDIS_FAIL_CLOSED` to `envConfigSchema` (default: `false` for development/testing resilience, set to `true` for high-security production).
2. **Fail-Closed Mode (`RATE_LIMIT_REDIS_FAIL_CLOSED=true`)**:
   - When Redis is unreachable or fails, `RateLimiterService` throws `HttpException(HttpStatus.SERVICE_UNAVAILABLE)` (`503 Service Unavailable`, `ErrorCode.SERVICE_UNAVAILABLE`).
   - Logs structured `SECURITY ALERT: Redis rate limiter unavailable under fail-closed policy. Rejecting request for key: ...`.
3. **Degraded In-Memory Mode (`RATE_LIMIT_REDIS_FAIL_CLOSED=false`)**:
   - Emits an explicit high-severity alert: `SECURITY WARNING: Redis rate limiter unavailable. Operating in degraded in-memory mode per node instance. Distributed rate limiting is not enforced across multiple replicas!`.
   - Returns `RateLimitResult` with `degraded: true`.
   - Sets response header `X-RateLimit-Degraded: true` via `RateLimitGuard` to alert downstream monitoring and API clients.
4. **Automated Verification**:
   - Unit test asserting `503 Service Unavailable` is thrown when Redis is offline and `failClosed=true`.
   - Unit test asserting `503 Service Unavailable` is thrown when Redis command throws runtime error and `failClosed=true`.
   - Unit test verifying `X-RateLimit-Degraded: true` header is set in degraded memory mode.
