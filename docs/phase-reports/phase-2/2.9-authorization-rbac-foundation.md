## 1. Executive Summary

Task 2.9 establishes a robust, enterprise-grade Role-Based Access Control (RBAC) and Multi-Tenant Resource Isolation layer across the MerQent platform. Built directly on top of the approved authentication layer (Task 2.8) and shared domain contracts (Task 2.7), this architecture strictly separates **authentication** (verifying identity) from **authorization** (verifying privileges and resource ownership).

Key architectural achievements:
- **Unified Permission Model**: A canonical set of 16 granular permissions and a definitive `ROLE_PERMISSIONS` matrix defined in `@merqent/shared-types` and shared across backend and frontend.
- **Declarative NestJS Decorators**: Reusable, metadata-driven decorators (`@Roles()`, `@RequirePermissions()`, `@CheckTenant()`, and `@Public()`).
- **Standardized Guard Pipeline**: Modular execution via `RolesGuard`, `PermissionsGuard`, and `TenantGuard`, producing consistent `401 Unauthorized` and `403 Forbidden` HTTP responses with descriptive messages.
- **Server-Side Multi-Tenant Isolation**: Hardened tenant isolation verifying user organization context (`firmId`) against request parameters, queries, and bodies, preventing IDOR and cross-firm data leaks while maintaining `PLATFORM_ADMIN` cross-tenant supervisory access.
- **Zero-Roundtrip Tenant Context**: The authenticated user's active tenant (`firmId`) and profile (`consultantProfileId`) are securely embedded in short-lived JWT access tokens during login/refresh, enabling constant-time `O(1)` tenant checks without database lookups.
- **Frontend Authorization Helpers**: Typed client-side helpers (`can`, `isRole`, `isTenantMember`, `canAccessRoute`) in `apps/web/lib/authorization.ts` providing seamless UI conditionally rendered navigation without compromising the backend's status as the sole security authority.

## 2. Roles & Permissions Architecture

### 2.1 Role Definitions
MerQent supports four canonical user roles defined in the database schema and shared types:
1. `PLATFORM_ADMIN`: MerQent platform operations, consultant verification, dispute arbitration, global analytics, and platform governance.
2. `PE_FIRM_ADMIN`: Private equity firm managing partners and operations leads with full administrative authority over their firm, projects, and firm team members.

## 3. NestJS Authorization Guards & Decorators

The authorization layer is decoupled from authentication into dedicated guards and decorators:

### 3.1 Decorators
- **`@Roles(...roles: UserRole[])`**: Associates required role(s) to a controller class or method handler via metadata key `roles`.
- **`@RequirePermissions(...permissions: Permission[])`**: Associates required permission(s) to an endpoint via metadata key `permissions`.
- **`@CheckTenant(paramName = 'firmId')`**: Designates that an endpoint operates on a tenant-specific resource, instructing the guard to inspect route parameter `:firmId` (or `:id`), query parameters, or request body.
- **`@Public()`**: Explicitly marks endpoints (e.g. login, health check) as public, bypassing authentication and authorization guards.

### 3.2 Guards Execution & Behavior

```
Incoming Request
       │
       ▼
 [JwtAuthGuard] ────────── If @Public() ─────────────────────────────► Allow
       │ (Validates JWT, attaches req.user)
       ▼
  [RolesGuard] ─────────── If @Public() or no @Roles() ──────────────► Next Guard
       │
       ├── User missing? ──────► 401 Unauthorized
       └── Role mismatch? ────► 403 Forbidden ("Role 'X' is not authorized")
       ▼
[PermissionsGuard] ─────── If @Public() or no @RequirePermissions() ─► Next Guard
       │
       ├── User missing? ──────► 401 Unauthorized
       └── Lacks perm? ───────► 403 Forbidden ("Role 'X' lacks required permissions [Y]")
       ▼
 [TenantGuard] ─────────── If @Public() or no @CheckTenant() ────────► Next Handler
       │
       ├── User is PLATFORM_ADMIN? ──► Allow (Cross-tenant oversight)
       ├── User missing firmId? ─────► 403 Forbidden ("User does not belong to an organization")
       └── firmId != req.firmId ─────► 403 Forbidden ("Access denied: Resource belongs to another organization")
       ▼
Controller Handler Executed
```

## 4. Multi-Tenant Resource Isolation

### 4.1 Server-Side Tenant Enforcement
MerQent's multi-tenant architecture prevents users from accessing or tampering with resources belonging to other private equity firms or organizations.

1. **Token Persistence**:
   During authentication (`AuthService.login` / `AuthService.rotateRefreshToken`), the user's `FirmMember.firmId` is looked up from PostgreSQL and embedded in the `JwtAccessPayload`.
2. **Instant Verification**:
   When `TenantGuard` intercepts a request decorated with `@CheckTenant('firmId')`:
   - It extracts the requested tenant ID from `request.params.firmId`, `request.params.id`, `request.query.firmId`, `request.body.firmId`, or header `x-organization-id`.
   - If no tenant parameter is supplied, it assumes the route operates on the user's own tenant and attaches `req.user.firmId`.
   - If a tenant parameter is supplied and does **not** match `req.user.firmId`, the request is immediately rejected with `403 Forbidden`.
3. **Platform Administrator Exception**:
   Users with role `PLATFORM_ADMIN` are permitted to inspect cross-tenant records (e.g. for customer support, dispute resolution, or compliance reviews).

## 5. Frontend Authorization Integration

Frontend authorization is implemented in [`apps/web/lib/authorization.ts`](file:///c:/Users/Vishal%20S%20Naik/MyProjects/MerQent/apps/web/lib/authorization.ts).

### 5.1 Typed Access Helpers
- **`can(user, permission)`**: Checks if the authenticated user has a specific permission.
- **`isRole(user, ...roles)`**: Validates if the user's role matches any of the specified roles.
- **`isTenantMember(user, firmId)`**: Validates if the user belongs to the requested tenant or is a platform admin.
- **`canAccessRoute(pathname, user)`**: Evaluates route authorization policies for navigation guards and page rendering.
- **`getRoleDisplay(role)`**: Returns user-friendly role labels for UI components (e.g. "Platform Administrator", "PE Firm Admin").

### 5.2 Client Route Access Policies

| Route Pattern | Required Access | Allowed Roles / Permissions |
| :--- | :--- | :--- |
| `/admin/*` | Authenticated | `PLATFORM_ADMIN` (`PLATFORM_ADMIN_ACCESS`) |
| `/projects/new` | Authenticated | `PE_FIRM_ADMIN`, `PE_FIRM_MEMBER` (`PROJECT_CREATE`) |
| `/projects/*` | Authenticated | `PE_FIRM_ADMIN`, `PE_FIRM_MEMBER`, `CONSULTANT_OPERATOR`, `PLATFORM_ADMIN` |
| `/consultants/*` | Authenticated | `PE_FIRM_ADMIN`, `PE_FIRM_MEMBER`, `PLATFORM_ADMIN` |
| `/connections/*` | Authenticated | Any authenticated user |
| `/auth/*` | Public | Unauthenticated / Public |
| `/` | Public | Unauthenticated / Public |

> [!IMPORTANT]
> Client-side route checks are strictly for user experience (preventing broken navigation and hiding unauthorized UI components). All security boundaries are independently enforced by backend NestJS guards.

## 7. Unresolved Risks & Next Phase

- **Fine-grained Resource Ownership**:
  Task 2.9 provides tenant-level isolation (`firmId`). Individual resource ownership checks (e.g. verifying that a consultant can only update their own profile ID or a PE firm member can only update projects assigned to them) will be added to domain services in subsequent workflow tasks (Phase 3).
- **Dynamic Policy Engine (ABAC)**:
  Current authorization is role-based with static permission mapping. If dynamic attribute-based access control (ABAC) is required (e.g. time-limited NDAs or engagement-specific file access), this foundation can be extended with Casbin or Casl policies without breaking existing contracts.
