## 3. Environment & Secret Handling Audit

1. **Secret Exposure Safeguards:**
   - No production secrets exist in `.env.example`, Dockerfiles, or git repository history.
   - Frontend container only receives `NEXT_PUBLIC_*` variables; sensitive secrets (`DATABASE_URL`, `JWT_*`, `STORAGE_SECRET_ACCESS_KEY`) are inaccessible to client bundles.
   - Validation errors explicitly omit attempted secret values to prevent log leakage.

2. **Weak-Secret & Default Protection:**
   - `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` enforce minimum 32 characters.
   - `METRICS_SCRAPE_KEY` enforces minimum 32 characters in production.
   - Default dev passwords (`merqent_dev_password`) and MinIO defaults (`minioadmin`) are flagged as development-only.

3. **Fail-Closed Semantics:**
   - If Redis is unavailable, rate limiting and malware queue processing fail safely.
   - If ClamAV is disabled or unavailable, uploaded files remain in `PENDING` status and cannot be marked `CLEAN`.

## 4. Container & Orchestration Hardening

1. **Least-Privilege Non-Root Execution:**
   - API: Runs as non-root user `nestjs` (`uid: 1001`, `gid: 1001`).
   - Web: Runs as non-root user `nextjs` (`uid: 1001`, `gid: 1001`).
2. **Health Check Probes:**
   - Liveness probe (`GET /api/v1/health/live`): Confirms Node.js event loop is responsive.
   - Readiness probe (`GET /api/v1/health/ready`): Validates database, Redis, and storage connectivity. Returns HTTP 503 when dependencies are disconnected.
3. **Network Isolation:**
   - Internal bridge network (`merqent-internal`) encapsulates database and caching backends.
   - In production, database and Redis ports should not be mapped to external host interfaces.
