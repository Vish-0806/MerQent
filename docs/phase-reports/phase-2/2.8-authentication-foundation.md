## 1. Executive Summary

Task 2.8 establishes MerQent's enterprise authentication foundation across the NestJS API (`apps/api`), PostgreSQL/Prisma database, Redis cache/revocation layer, and Next.js frontend (`apps/web`).

The implementation follows industry best practices:
- **Argon2id password hashing** for state-of-the-art resistance against GPU/ASIC attacks.
- **Input validation** via canonical Zod schemas from `@merqent/validation` (`RegisterUserSchema`, `LoginUserSchema`) paired with NestJS `class-validator` and OpenAPI Swagger documentation.
- **Dual-token JWT architecture**: short-lived (15-minute) access tokens and securely persisted, rotated (7-day) refresh tokens.
- **Cryptographic token safety**: refresh tokens are never stored in plaintext; high-entropy SHA-256 hashes are persisted in the `RefreshToken` PostgreSQL table.
- **Automatic token rotation and compromised reuse detection**: presenting an already revoked refresh token triggers an immediate security alert and invalidates all active sessions for that user.
- **Redis revocation blacklist**: instantaneous, cluster-wide revocation upon logout or token compromise with automatic TTL expiration.
- **Secure browser integration**: refresh tokens are transmitted and managed exclusively via `HttpOnly`, `SameSite=lax` (or `strict`), `Secure` cookies with credentialed CORS; client-side access tokens are kept exclusively in memory to eliminate XSS token exfiltration risks.

## 2. Authentication Endpoints Implemented

All endpoints are hosted under `/api/v1/auth` with OpenAPI Swagger tags:

| HTTP Method | Route | Access | Request Body / Cookies | Response Body | Description |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `POST` | `/api/v1/auth/register` | Public | `RegisterDto` (`email`, `password`, `fullName`, `role`) | `AuthResponseDto` (`accessToken`, `user`) + HttpOnly cookie | Registers user with Argon2id hash, creates active account, issues dual tokens, sets refresh cookie. |
| `POST` | `/api/v1/auth/login` | Public | `LoginDto` (`email`, `password`) | `AuthResponseDto` (`accessToken`, `user`) + HttpOnly cookie | Validates credentials, checks account status, updates `lastLoginAt`, sets refresh cookie. |
| `POST` | `/api/v1/auth/refresh` | Public | HttpOnly Cookie `refresh_token` (or fallback body/header) | `AuthResponseDto` (`accessToken`, `user`) + rotated HttpOnly cookie | Verifies refresh JWT, revokes old token in DB + Redis, issues new rotated token pair. |
| `POST` | `/api/v1/auth/logout` | Public | HttpOnly Cookie `refresh_token` (or fallback body/header) | `{ success: true, message: string }` + Cleared cookie | Revokes token in DB, blacklists token ID in Redis, clears HttpOnly cookie. |
| `GET` | `/api/v1/auth/me` | Protected (`Bearer JWT`) | None (Header `Authorization: Bearer <token>`) | `SanitizedUserDto` | Returns authenticated user profile using `JwtAuthGuard` and `@CurrentUser()`. |

## 3. Token & Session Lifecycle

```
[Client]                                  [NestJS API]                        [PostgreSQL / Redis]
   |                                            |                                      |
   |-- 1. POST /login ------------------------->|                                      |
   |   (email, password)                        |-- Verify Argon2id hash ------------->|
   |                                            |-- Create RefreshToken record (DB) -->|
   |<-- 2. 200 OK (Set-Cookie + accessToken) ---|                                      |
   |                                            |                                      |
   |-- 3. GET /me (Authorization: Bearer JWT) ->|-- Validate JWT signature ------------|
   |<-- 4. 200 OK (Sanitized User Profile) -----|                                      |
   |                                            |                                      |
   |-- 5. POST /refresh (HttpOnly cookie) ----->|-- Verify JWT signature -------------|
   |                                            |-- Check Redis blacklist ------------>|
   |                                            |-- Check DB record & SHA-256 hash --->|
   |                                            |-- Mark old token isRevoked=true ---->|
   |                                            |-- Add old token to Redis blacklist ->|
   |                                            |-- Create NEW RefreshToken record --->|
   |<-- 6. 200 OK (New Cookie + New Access JWT)-|                                      |
   |                                            |                                      |
   |-- 7. POST /logout ------------------------>|-- Mark token isRevoked=true (DB) --->|
   |                                            |-- Blacklist token ID in Redis ------>|
   |<-- 8. 200 OK (Clear-Cookie) ---------------|                                      |
```

### Security Decisions:
1. **No Plaintext Tokens**: Raw refresh tokens are never persisted in the database. The API computes a SHA-256 hash of the high-entropy token string and indexes `tokenHash` in `refresh_tokens`.
2. **Compromised Token Reuse Detection**: If a revoked refresh token is presented, the system immediately recognizes a potential replay attack or stolen session, logs a high-severity security alert, and bulk-revokes all active sessions (`updateMany({ where: { userId, isRevoked: false }, data: { isRevoked: true } })`).
3. **Redis Revocation Blacklist**: Whenever a session is rotated or terminated, the token ID (`jti`) is stored in Redis with an exact TTL matching the remaining lifespan of the token. Lookups take sub-millisecond time.
4. **Timing-Safe Login Failures**: If an email is not found, a dummy Argon2id hash is computed before throwing a generic `UnauthorizedException('Invalid email or password')`, mitigating user enumeration attacks.
5. **No Token Exposure in Browser Storage**: `localStorage` and `sessionStorage` are strictly avoided. Client access tokens reside purely in memory in `apps/web/lib/auth.ts`, protecting against malicious scripts or browser extensions reading credentials.

## 4. Database & Redis Infrastructure Integration

- **PostgreSQL 16 with pgvector (Host Port 5433)**:
  - Models utilized: `User` and `RefreshToken` (from canonical schema).
  - Cascade deletion on user removal.
  - Compound index on `[userId, isRevoked]`.
- **Redis 7.2 Alpine (Host Port 6379)**:
  - Provided by `RedisService` (`apps/api/src/infrastructure/redis/redis.service.ts`) with lazy connection, exponential retry, and clean shutdown handling.
  - Used for immediate blacklist lookups and cluster-wide session invalidation.

---

## 5. Web Application Integration

- **API Client Update (`apps/web/lib/api-client.ts`)**:
  - Configured `credentials: 'include'` by default for all requests.
  - Supports Bearer token authorization header injection from memory.
- **Frontend Auth Helper (`apps/web/lib/auth.ts`)**:
  - `authStorage`: in-memory token getter/setter/clearer.
  - `authApi`: typed wrappers for `login`, `register`, `refresh`, `logout`, and `getMe`.
  - Automated silent refresh capability via HttpOnly cookies without exposing refresh secrets.
