MerQent Task 2.15 delivers a production-grade, highly resilient background job infrastructure built on **BullMQ** and the existing Redis configuration. The implementation strictly decouples queue registration, job production, worker processing, and lifecycle management within a dedicated NestJS `JobsModule`.

The design rigorously enforces all security and reliability constraints:
1. **Zero Secret Leakage:** Job payloads and structured logs contain only minimal entity UUIDs and storage keys. Passwords, auth tokens, presigned URLs, and file streams are strictly forbidden.
2. **Ground-Truth Authorization Verification:** Background workers independently verify tenant ownership and storage key alignment against PostgreSQL ground truth before processing jobs.
3. **Fail-Closed Malware Lifecycle:** As mandated by Task 2.14 and Task 2.14.1, background malware jobs fail closed when the scanner daemon is unattached or inactive (`isLive = false`), leaving files in `PENDING` status. Infected files trigger immediate storage deletion and quarantine.
4. **Bounded Growth & Graceful Lifecycle:** Redis memory exhaustion is prevented through bounded retention (`removeOnComplete` / `removeOnFail`). Workers pause in-flight execution on application shutdown signals and cleanly close Redis connections during module destruction.


### 2.2 Redis Connection Configuration
BullMQ workers require strict Redis client configurations. `AppConfigService` was updated to supply `redisConnectionOptions`:
- `maxRetriesPerRequest: null` (mandatory requirement for BullMQ blocking commands)
- `enableReadyCheck: false`
- Optional password authentication support via `REDIS_PASSWORD`

### 2.3 Separation of Concerns
- **Queue Registration:** Managed centrally in `JobsService` during `onModuleInit`. Backing BullMQ `Queue` instances are injected into producers via dependency injection.
- **Job Producers (`FileQueueProducer`):** Enforce strict Zod input validation (`MalwareScanJobPayloadSchema`, `CleanupAbandonedJobPayloadSchema`) and attach deterministic deduplication keys before dispatching to BullMQ.
- **Worker Processors (`FileQueueProcessor`):** Execute jobs in isolated worker worker concurrency pools (concurrency = 5) delegating to domain services without exposing queue administration.

## 3. Reliability & Lifecycle Controls

### 3.1 Bounded Retries & Exponential Backoff
All queue jobs are configured with bounded retry policies:
- **Max Attempts:** 3 bounded attempts.
- **Backoff Strategy:** Exponential backoff starting at 1,000ms delay.
- **Controlled Error Propagation:** Transient infrastructure errors (e.g. scanner connection timeouts) rethrow to trigger BullMQ retries, while permanent security violations abort immediately without wasteful retries.

### 3.2 Redis Memory Retention Bounds
To prevent unbounded Redis memory growth from high-volume operations:
- **Completed Jobs:** Kept up to `1,000` jobs or a max age of `3,600` seconds (1 hour).
- **Failed Jobs:** Kept up to `5,000` jobs or a max age of `86,400` seconds (24 hours) for auditing and inspection.

### 3.3 Graceful Shutdown Sequence
The application lifecycle hooks ensure zero interrupted jobs during rolling deployments:
1. `beforeApplicationShutdown()`: Invokes `worker.pause(true)`, preventing the worker from picking up new jobs while allowing in-flight jobs to complete.
2. `onModuleDestroy()`: Awaits `worker.close()` and `queue.close()`, disconnecting Redis sockets cleanly.

### 3.4 Idempotency & Deduplication
- **Deterministic Job IDs:** Malware scan jobs use `jobId = malware-scan:${fileRecordId}`, preventing duplicate scan jobs from queuing for the same file.
- **In-Processor State Verification:** If a file has already transitioned to `CLEAN` or `INFECTED`, duplicate delivery safely skips I/O and completes idempotently.

## 4. Security & Access Control

### 4.1 Payload Minimality & Validation
Payloads are strictly validated via `@merqent/validation` Zod schemas before enqueueing:
- `MalwareScanJobPayloadSchema`: Only accepts `fileRecordId` (UUID), `storageKey`, optional `requestedByUserId` (UUID), and optional `tenantId`.
- Sensitive data (credentials, bearer tokens, presigned URLs, and binary contents) are strictly excluded from job payloads and structured logging.

### 4.2 Ground-Truth Authorization Verification
Workers do not trust tenant IDs provided in queued payloads:
1. The worker fetches the `FileRecord` from PostgreSQL ground truth.
2. It verifies that `fileRecord.storageKey === payload.storageKey`.
3. It confirms that the object path strictly matches tenant isolation rules (`tenants/${tenantId}/`).
4. Any discrepancy triggers a logged security alert and immediate job failure.

### 4.3 Queue Administration Restriction
No public HTTP endpoints or dashboards (such as Bull-Board) are exposed. Queue operational metrics are only accessible through internal NestJS dependency injection and the authenticated/readiness health probe.

## 5. File Lifecycle & Malware Scanner Integration

### 5.1 Fail-Closed Security Policy
In accordance with Task 2.14 and Task 2.14.1:
- If the configured `IMalwareScanner` indicates `isLive = false`, the worker logs a security boundary diagnostic and leaves the file status as `PENDING`.
- Files are **never** marked `CLEAN` without positive verification from an active scanner.

### 5.2 Quarantine & Purge
When malware is detected by an active scanner:
1. The object is immediately purged from S3 storage via `storage.deleteFile(storageKey)`.
2. The database record is marked `FileScanStatus.INFECTED`.
3. The event is logged as a high-severity security alert.

### 5.3 Abandoned Upload Cleanup
The `cleanup-abandoned` job:
- Finds file records remaining in `FileScanStatus.PENDING` older than `maxAgeHours` (default 24h).
- Deletes storage files from S3 and cleans up orphaned database records using race-safe queries.

## 6. Observability & Health Probes

Queue health is integrated into `/health` and `/health/ready` via `AppController`:
- Queue metrics: waiting, active, and failed job counts.
- Worker status: `running`, `paused`, or `stopped`.
- Degraded threshold: Triggers `degraded` status if failed jobs exceed 20 or the queue is paused.
- Readiness check: Sets `503 SERVICE UNAVAILABLE` if background worker/queue is unhealthy or Redis disconnected.
