MerQent Task 2.16 establishes a production-grade, highly scalable, and secure realtime communication infrastructure for the platform. Built on **Socket.IO** and backed by **Redis Pub/Sub adapter clustering**, this layer provides a decoupled, resilient foundation for bi-directional event transport without coupling realtime transport mechanics to marketplace business domain logic.

The implementation strictly satisfies all architectural and security constraints:
1. **Zero Client Trust:** WebSocket connections authenticate exclusively via cryptographically signed JWT access tokens. User identity, roles, and tenant firm memberships are never accepted from client-supplied handshake parameters; they are resolved directly against PostgreSQL database ground truth.
2. **Server-Enforced Tenant Room Isolation:** Sockets are automatically bound to verified tenant rooms (`user:${userId}`, `firm:${firmId}`). Arbitrary room joining is prevented through server-side authorization checks.
3. **Redis Scalability with Resilient In-Memory Fallback:** Multi-instance clustering operates via `@socket.io/redis-adapter`. In the event of Redis downtime, the adapter gracefully falls back to local in-memory event dispatching without crashing or terminating client connections.
4. **Denial-of-Service & Abuse Mitigation:** Strict connection concurrency caps (max 10 active sockets per user), sliding-window event rate limiting (max 30 events per 10 seconds per socket), buffer size caps (`maxHttpBufferSize = 64KB`), and explicit CORS origin checks are enforced server-side.
5. **Session Revocation & Active Token Expiry Enforcement:** Handshake verifies token blacklisting in Redis. Active sockets undergo revocation and account status checks during periodic heartbeat events, immediately disconnecting revoked sessions.
6. **Zero Sensitive Data Leakage:** Structured lifecycle logging strictly omits JWT tokens, deal contents, presigned URLs, and user messages.

### 2.3 Domain Decoupling via `RealtimeService`
Realtime transport mechanics are cleanly separated from application domain logic:
- Domain services and controllers do not interact with raw `Socket` instances or `@WebSocketGateway`.
- Domain services inject `RealtimeService` to publish events:
  - `emitToUser(userId, event, payload)`: Delivers targeted notifications to all connected devices for a user.
  - `emitToFirm(firmId, event, payload)`: Delivers updates to all members within a verified firm.
  - `emitToRoom(roomId, event, payload)`: Broadcasts to arbitrary verified rooms.
  - `disconnectUser(userId, reason)`: Forcibly terminates active sockets when a user is suspended or logged out.

## 3. Authentication & Authorization Architecture

### 3.1 Handshake Authentication Sequence
When a client connects to `ws://api.merqent.com/realtime`:
1. **Token Extraction:** The gateway extracts the JWT access token from `handshake.auth.token` or the `Authorization: Bearer <token>` header. If missing, connection is immediately rejected (`401 Unauthorized`).
2. **Cryptographic Verification:** The token is validated using `JwtService.verifyAsync()` against the system's `jwt.secret`. Expired or invalid signatures are rejected.
3. **Revocation Blacklist Check:** The token is checked against Redis (`isTokenBlacklisted()`). If found, connection is rejected.
4. **Ground-Truth User Resolution:** The user is queried from PostgreSQL (`prisma.user.findUnique`) selecting `id`, `email`, `role`, `status`, and `firmMember.firmId`.
5. **Account Status Verification:** If `user.status !== UserStatus.ACTIVE` (e.g. `SUSPENDED` or `PENDING_VERIFICATION`), connection is denied.
6. **Concurrent Connection Throttling:** The gateway counts active sockets for `user:${userId}`. If `count >= WS_MAX_CONNECTIONS_PER_USER` (10), connection is terminated with a rate limit error to prevent resource starvation.
7. **Session Binding & Room Attachment:** The client socket attaches `socket.data.user = WsAuthenticatedUser` and automatically joins `user:${userId}` and `firm:${firmId}`. An acknowledgment event `connection:established` is emitted.

### 3.2 Tenant Room Authorization
Clients can request to join additional rooms via `room:join`:
- **Payload Validation:** Enforced via `WsJoinRoomSchema` (`roomId` must be a non-empty string max 128 characters).
- **Tenant Isolation Check:**
  - `firm:<targetFirmId>`: Allowed only if `user.firmId === targetFirmId` or `user.role === UserRole.PLATFORM_ADMIN`.
  - `user:<targetUserId>`: Allowed only if `user.id === targetUserId` or `user.role === UserRole.PLATFORM_ADMIN`.
  - Any attempt to join another firm's room is denied with `WS_ROOM_JOIN_DENIED`.

### 3.3 Active Session Revocation on Heartbeat
Clients send periodic `heartbeat` events:
- The gateway verifies whether the token has been added to the Redis blacklist or if the user account status was changed to `SUSPENDED`.
- If revoked, the socket is immediately disconnected (`socket.disconnect(true)`).
- Valid heartbeats respond with `heartbeat:ack` containing the current server timestamp.

## 4. Redis Scalability & Adapter Clustering

### 4.1 Multi-Instance Redis Adapter
To support horizontal scaling of API instances without relying on single-node in-memory state:
- `RedisIoAdapter` implements `@socket.io/redis-adapter` using two dedicated `ioredis` connections (`pubClient` and `subClient`).
- Broadcasts to rooms (e.g., `emitToFirm`) are distributed across all API instances via Redis Pub/Sub channels.

### 4.2 Fault Tolerance & In-Memory Fallback
- If Redis is unavailable during boot or encounters a network partition:
  - `RedisIoAdapter` catches the connection error and logs a warning.
  - The adapter switches `isConnected = false` and continues operating in **in-memory fallback mode**.
  - Local WebSocket connections remain functional on each pod.
  - When Redis reconnects, the adapter re-attaches pub/sub channels automatically.

## 5. Security, Privacy & Rate Limiting

### 5.1 Defense-in-Depth Protections
1. **Payload Schema Validation:** Handled via `@merqent/validation` Zod schemas (`WsJoinRoomSchema`, `WsLeaveRoomSchema`, `WsHeartbeatSchema`). Invalid payloads trigger structured `error` events with code `WS_INVALID_PAYLOAD`.
2. **Payload Size Bounds:** Enforced at the engine layer via `maxHttpBufferSize = 64KB` (65,536 bytes). Oversized frames are dropped by Socket.IO before parsing.
3. **Sliding-Window Event Rate Limiting:**
   - Window: `10,000 ms` (10 seconds)
   - Max events: `30`
   - Excess events trigger `WS_RATE_LIMIT_EXCEEDED` warnings. Persistent flooding triggers socket disconnection.
4. **Strict CORS Allowlist:** Evaluated on every WebSocket upgrade handshake against configured origins. Wildcards (`*`) are prohibited.
5. **Log Privacy:** No auth tokens, user message payloads, or presigned URLs are logged in stdout or structured logger streams.

## 6. Observability & Health Probes

### 6.1 Realtime Health Reporting
`RealtimeService.checkHealth()` provides non-sensitive realtime operational metrics:
- `status`: `'healthy'` (Redis adapter connected) | `'degraded'` (in-memory fallback) | `'disconnected'`.
- `adapterStatus`: `'connected'` | `'disconnected'` | `'fallback'`.
- `activeConnections`: Total count of active WebSocket connections.
- `roomsCount`: Total active room count across the gateway.

### 6.2 Health Probes Integration
- **Liveness Probe (`/health`):** Includes `dependencies.realtime` status.
- **Readiness Probe (`/health/ready`):**
  - If realtime status is `'degraded'` (running on in-memory fallback), readiness succeeds (`ready: true`) to avoid cascading outages of the HTTP REST API.
  - If realtime status is `'disconnected'` (e.g. gateway initialization failure), readiness fails (`503 Service Unavailable`).
